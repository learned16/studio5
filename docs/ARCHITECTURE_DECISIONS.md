# Architecture Decisions

## ADR-001: Modular Monolith

**قرار:** يبدأ التطبيق Modular Monolith، لا Microservices.  
**السبب:** مستخدم واحد ونافذة تنفيذ ثلاثة أشهر.  
**الحدود:** Core، Academic، Files/Artifacts، Notes/Ink، Tasks/Schedule، Search، Sync/Backup، Drawing Coach، AI Adapter.  
**الأثر:** وحدات داخل تطبيق واحد مع واجهات واضحة بين Domains.

## ADR-002: Local-first

قاعدة بيانات محلية هي مصدر العمل اليومي. السحابة/المزامنة/AI حدود فشل منفصلة. لا يعامل التخزين المحلي كـcache هش.

## ADR-003: Stable IDs وSchemas

كل كيان يملك Stable ID لا يتغير. كل schema تحمل إصداراً، وكل تعديل يملك Migration مختبرة وRollback أو Recovery موثقاً.

## ADR-004: Subject Profiles وCapability Packs

Subject لا ينشئ شاشات خاصة باسم مادة. Profile يحدد نوع المادة، وCapability Packs تفعل الأدوات مثل exercises أو problem notebook أو materials cards. لا تثبت مواد السنة الأولى في Core.

## ADR-005: ملفات وأحبار غير متلفة

الأصل PDF/الملف Immutable. annotations وink وpreviews وderived artifacts منفصلة، مع hash وversion record ومصدر.

## ADR-006: Feature Flags

كل قدرة اختيارية أو مستقبلية خلف Feature Flag. لا تستخدم Flags لإخفاء Must Have من دون Change Control.

## ADR-007: AI Provider Abstraction

واجهة Provider مستقلة عن OpenAI أو Claude. لا يوضع مفتاح API في العميل. AI اختياري؛ سلاسل الدراسة المحلية لا تعتمد عليه.

## ADR-008: تقنية واجهة السنة الأولى ومحرك Ink

**الحالة:** `Proposed - Needs User Decision`
**التاريخ:** 2026-07-25

### السياق

كان اختيار التقنية مؤجلاً إلى ما بعد اختبار القلم والحفظ والاستعادة والتصدير على جهاز
`HUAWEI MatePad 11.5 PaperMatte`. اكتملت الآن الاختبارات الوظيفية على الجهاز الحقيقي.

### الدليل الفعلي

| المعيار | Web/PWA الحالي | Kotlin/Native | Flutter |
|---|---|---|---|
| ضغط قلم Huawei | PASS على الجهاز | لم يُبن Prototype | لم يُبن Prototype |
| Palm rejection بعد الإصلاح | PASS على الجهاز | غير مختبر | غير مختبر |
| الممحاة المقطعية | PASS على الجهاز | غير مختبر | غير مختبر |
| Force Kill + Recovery | PASS بلا فقد | غير مختبر | غير مختبر |
| جلسة رسم 15 دقيقة | PASS بلا تأخير ملحوظ | غير مختبر | غير مختبر |
| قرابة 1000 stroke | PASS للحفظ وإعادة الفتح | غير مختبر | غير مختبر |
| Offline وExport | PASS | ممكن نظرياً | ممكن نظرياً |
| سرعة التطوير والنشر على أجهزة متعددة | عالية | أقل ومقيدة أكثر بالمنصة | متوسطة |

المقارنة لا تدعي أن Web أسرع نظرياً من البدائل؛ بل إن Web/PWA هو الخيار الوحيد الذي
يملك دليلاً فعلياً ناجحاً على الجهاز المستهدف حالياً.

### البدائل

1. **اعتماد Web/PWA للسنة الأولى:** يبني فوق الدليل الحالي ويحافظ على سرعة التطوير والوصول من التابلت.
2. **Kotlin/Native:** قد يمنح تكاملاً أعمق مع Android والقلم، لكنه يحتاج Prototype جديداً وإعادة تنفيذ قبل وجود فشل يبرره.
3. **Flutter:** يوفر Cross-platform وتغليف تطبيق، لكنه يحتاج Prototype قلم ومقارنة جديدة ولا يملك دليلاً أفضل حالياً.
4. **Web داخل Native wrapper لاحقاً:** خيار ترقية إذا احتجنا توزيع تطبيق أو API جهاز لا توفره PWA، من دون استبدال Core.

### التوصية

اعتماد **Web/PWA كتقنية واجهة السنة الأولى ومحرك Ink الحالي**، مع إبقاء حدود `Ink`,
والتخزين، والتصدير منفصلة عن الواجهة حتى يمكن تغليفها أو استبدال محرك العرض لاحقاً إذا
ظهر سبب مثبت.

### محفزات إعادة التقييم

- فقد بيانات أو فشل Recovery على الجهاز الحقيقي.
- تأخير ملحوظ ومتكرر عند أحجام استخدام السنة الأولى الفعلية.
- حاجة إلزامية إلى API للقلم أو النظام لا توفرها PWA.
- تعذر تشغيل PDF/Notebook/Ink معاً ضمن معايير الأداء المقبولة.

### الأثر

- لا إعادة بناء للـCore أو البيانات عند إضافة سنوات لاحقة.
- نستمر بالمسار المثبت بدلاً من تمويل ثلاثة Prototypes متوازية.
- يبقى القياس الكمي للأداء ضمن Hardening.
- لا تتحول هذه التوصية إلى `Adopted` إلا بموافقة المستخدم الصريحة.

### القرار المطلوب من المستخدم

هل تعتمد Web/PWA كتقنية نسخة السنة الأولى وفق هذه الحدود ومحفزات إعادة التقييم؟
