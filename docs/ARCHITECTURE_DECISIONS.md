# Architecture Decisions

## ADR-001: Modular Monolith

**قرار:** يبدأ التطبيق Modular Monolith، لا Microservices.  
**السبب:** مستخدم واحد ونافذة تنفيذ ثلاثة أشهر.  
**الحدود:** Core، Academic، Files/Artifacts، Notes/Ink، Tasks/Schedule، Search، Sync/Backup، Drawing Coach، AI Adapter.  
**الأثر:** وحدات داخل تطبيق واحد مع واجهات واضحة بين Domains.

## ADR-002: Local-first

قاعدة بيانات محلية هي مصدر العمل اليومي. السحابة/المزامنة/AI حدود فشل منفصلة. لا يعامل التخزين المحلي كـcache هش.

## ADR-003: Stable IDs وSchemas

كل كيان يملك Stable ID لا يتغير. كل schema تحمل إصداراً، وكل تعديل يملك Migration مختبرة وRollback أو Recovery موثقاً.

## ADR-004: Subject Profiles وCapability Packs

Subject لا ينشئ شاشات خاصة باسم مادة. Profile يحدد نوع المادة، وCapability Packs تفعل الأدوات مثل exercises أو problem notebook أو materials cards. لا تثبت مواد السنة الأولى في Core.

## ADR-005: ملفات وأحبار غير متلفة

الأصل PDF/الملف Immutable. annotations وink وpreviews وderived artifacts منفصلة، مع hash وversion record ومصدر.

## ADR-006: Feature Flags

كل قدرة اختيارية أو مستقبلية خلف Feature Flag. لا تستخدم Flags لإخفاء Must Have من دون Change Control.

## ADR-007: AI Provider Abstraction

واجهة Provider مستقلة عن OpenAI أو Claude. لا يوضع مفتاح API في العميل. AI اختياري؛ سلاسل الدراسة المحلية لا تعتمد عليه.

## ADR-008: تقنية واجهة السنة الأولى ومحرك Ink

**الحالة:** `Adopted`
**التاريخ:** 2026-07-25

### السياق

كان اختيار التقنية مؤجلاً إلى ما بعد اختبار القلم والحفظ والاستعادة والتصدير على جهاز
`HUAWEI MatePad 11.5 PaperMatte`. اكتملت الآن الاختبارات الوظيفية على الجهاز الحقيقي.

### الدليل الفعلي

| المعيار | Web/PWA الحالي | Kotlin/Native | Flutter |
|---|---|---|---|
| ضغط قلم Huawei | PASS على الجهاز | لم يُبن Prototype | لم يُبن Prototype |
| Palm rejection بعد الإصلاح | PASS على الجهاز | غير مختبر | غير مختبر |
| الممحاة المقطعية | PASS على الجهاز | غير مختبر | غير مختبر |
| Force Kill + Recovery | PASS بلا فقد | غير مختبر | غير مختبر |
| جلسة رسم 15 دقيقة | PASS بلا تأخير ملحوظ | غير مختبر | غير مختبر |
| قرابة 1000 stroke | PASS للحفظ وإعادة الفتح | غير مختبر | غير مختبر |
| Offline وExport | PASS | ممكن نظرياً | ممكن نظرياً |
| سرعة التطوير والنشر على أجهزة متعددة | عالية | أقل ومقيدة أكثر بالمنصة | متوسطة |

المقارنة لا تدعي أن Web أسرع نظرياً من البدائل؛ بل إن Web/PWA هو الخيار الوحيد الذي
يملك دليلاً فعلياً ناجحاً على الجهاز المستهدف حالياً.

### البدائل

1. **اعتماد Web/PWA للسنة الأولى:** يبني فوق الدليل الحالي ويحافظ على سرعة التطوير والوصول من التابلت.
2. **Kotlin/Native:** قد يمنح تكاملاً أعمق مع Android والقلم، لكنه يحتاج Prototype جديداً وإعادة تنفيذ قبل وجود فشل يبرره.
3. **Flutter:** يوفر Cross-platform وتغليف تطبيق، لكنه يحتاج Prototype قلم ومقارنة جديدة ولا يملك دليلاً أفضل حالياً.
4. **Web داخل Native wrapper لاحقاً:** خيار ترقية إذا احتجنا توزيع تطبيق أو API جهاز لا توفره PWA، من دون استبدال Core.

### التوصية

اعتماد **Web/PWA كتقنية واجهة السنة الأولى ومحرك Ink الحالي**، مع إبقاء حدود `Ink`,
والتخزين، والتصدير منفصلة عن الواجهة حتى يمكن تغليفها أو استبدال محرك العرض لاحقاً إذا
ظهر سبب مثبت.

### محفزات إعادة التقييم

- فقد بيانات أو فشل Recovery على الجهاز الحقيقي.
- تأخير ملحوظ ومتكرر عند أحجام استخدام السنة الأولى الفعلية.
- حاجة إلزامية إلى API للقلم أو النظام لا توفرها PWA.
- تعذر تشغيل PDF/Notebook/Ink معاً ضمن معايير الأداء المقبولة.

### الأثر

- لا إعادة بناء للـCore أو البيانات عند إضافة سنوات لاحقة.
- نستمر بالمسار المثبت بدلاً من تمويل ثلاثة Prototypes متوازية.
- يبقى القياس الكمي للأداء ضمن Hardening.
- تحولت التوصية إلى `Adopted` بعد موافقة المستخدم الصريحة.

### القرار المعتمد

اعتمد المستخدم Web/PWA كتقنية نسخة السنة الأولى وفق هذه الحدود ومحفزات إعادة التقييم
بتاريخ 2026-07-25.

## ADR-009: واجهات تجريبية قابلة للاستبدال

**قرار:** كل واجهة أو تدفق يُبنى قبل الاستعمال الجامعي الحقيقي يبقى `Experimental`، وتفصل ملفاته عن Core وعن بقية واجهات التجارب.

**السبب:** المتطلبات الحالية مبنية على توقعات قبل بدء الدوام. قد يثبت الاستخدام الحقيقي أن شكلاً ما ضعيف أو غير مفيد أو يحتاج إعادة تصميم جوهرية.

**الحدود المعمارية:**

1. `Core/Domain`: المعنى والبيانات والعقود المستقرة.
2. `Adapter/Bridge`: ترجمة العقد إلى احتياج السطح.
3. `Prototype UI`: تجربة قابلة لإعادة البناء.
4. `Deployment`: إعداد نشر مستقل للسطح عند الحاجة.

لا يستورد Prototype ملفات Prototype آخر مباشرة، ولا يُنقل منطق المجال إلى UI لتسريع التجربة.

**الأثر:** يمكن تعديل أو استبدال أو تقاعد واجهة Capture أو Ink أو أي تجربة لاحقة من دون هدم بقية النظام. تبقى البيانات محفوظة، وأي تغيير Schema يمر عبر Migration وRecovery.

**حالات النضج:** `Experimental -> Accepted | Revise | Retired`. النجاح التقني وحده لا ينقل الميزة إلى `Accepted`؛ يحتاج استعمالاً حقيقياً وقرار مستخدم.

## ADR-010: هوية تخزين متصفح موحدة مع مهاجرة غير متلفة

**قرار:** تعتمد واجهات Lecture وLibrary وReliability أسماء التخزين المركزية
`studio5-core` و`studio5-file-content` من Storage Profile واحد داخل Core. تُنسخ
بيانات أسماء Phase 3 القديمة مرة واحدة فقط بعد التحقق، ولا يُحذف المصدر القديم.

**السبب:** استمرار كل Prototype باسم IndexedDB مستقل يجعل النسخ الاحتياطي والاستعادة
والتوسع اللاحق يريان مخازن مختلفة، وقد يظهر للمستخدم مخزن فارغ بعد تغيير الاسم.

**قواعد السلامة:**

1. المهاجرة idempotent ويمكن إعادة تشغيلها بلا تكرار.
2. لا يُستبدل مخزن معتمد غير فارغ ومختلف بصمت.
3. أي تعارض يوقف الاعتماد ويعرض نتيجة صريحة.
4. فشل النسخ لا يحذف أو يعدّل المصدر القديم.
5. اختلاف أصل المتصفح لا يُتجاوز بحيلة داخل IndexedDB؛ يحتاج Export/Import صريحاً
   أو مساراً موحداً في مهمة مستقلة.

**الأثر:** تصبح واجهات الموقع الحالي فوق هوية تخزين واحدة قابلة للنسخ والاستعادة،
مع بقاء بيانات Ink Lab القديم آمنة على أصلها وعدم الادعاء بأنها نُقلت تلقائياً.

**الحالة:** `Adopted / PDF-NOTES DEVICE PASS / FULL PHASE 4 GATE PENDING` بتاريخ
2026-07-31. أثبتت إعادة التحميل وإغلاق المتصفح وإعادة فتحه بقاء PDF والملاحظات
بلا تكرار على MatePad؛ لم تُختبر بعد استعادة Backup الكامل مع Ink وTasks.

## ADR-011: GitHub هو المصدر الوحيد وSites مرجع مجمّد

**قرار:** مستودع GitHub وفروعه هما المصدر الوحيد لكود Studio5 وتاريخه ومراجعاته.
يُوقف نشر أي تحديث جديد إلى ChatGPT Sites، ولا يُعدّل الكود ليتوافق معه. يبقى نشر
Sites v9 الحالي مؤقتاً كمرجع معاينة فقط من دون حذفه الآن.

**السبب:** المرحلة التالية تحتاج معاينات مرتبطة مباشرة بكل Branch وPull Request،
مع فصل البناء المستقل عن مزود استضافة واحد.

**الأثر:**

1. كل Build وCI وPR يبدأ من GitHub.
2. يجب أن ينجح P0 وP3 كتطبيقي ويب مستقلين وينتجا مجلد `dist/`.
3. لا يمثل نجاح Sites أو فشله بوابة قبول للمنتج.
4. يبقى اختبار MatePad يدوياً مطلوباً ولا تستبدله معاينة ويب آلية.

**الحالة:** `Adopted` بقرار المستخدم بتاريخ 2026-07-29.

## ADR-012: النجاح الوظيفي منفصل عن اعتماد تصميم الواجهة

**الحالة:** `Adopted`

**قرار:** واجهتا P3 وP0 الحاليتان Functional Prototypes وليستا تصميم Studio5
النهائي. نجاح PDF/Notes في P3 على MatePad يغلق بوابتهما الجزئية فقط، ولا يغلق
Ink داخل Worker أو Full Backup/Restore.

**السبب:** أثبتت الواجهة عمليات PDF وNotes والحفظ وإعادة الفتح، بينما صُممت
أساساً لعزل المخاطر والاختبار السريع ولم تُبنَ كـApp Shell موحد للاستخدام
الجامعي اليومي.

**الأثر:**

1. لا تُحذف أو تُعاد كتابة واجهة P3 الآن.
2. لا يتغير Core أو Schema أو Storage أو Backup.
3. Phase 4.5 مرحلة UI/UX فقط وتستخدم العقود الحالية.
4. النقل اللاحق يتم Route-by-route مع Functional Parity وFeature Flag وRollback.
5. لا يبدأ كود Phase 4.5 أو Phase 5 قبل مراجعة المستخدم للمواصفة.

**المرجع:** `docs/PHASE_4_5_UX_FOUNDATION_SPEC_AR.md`.

## ADR-013: اتجاه المنتج وبنية التنقل في Phase 4.5

**الحالة:** `Adopted`

**قرار:** الاتجاه البصري `Warm Paper Academic Studio`. Product Shell باللغة
الإنكليزية وباتجاه LTR، مع اتجاه تلقائي لمحتوى المستخدم العربي والمختلط.
التنقل الرئيسي هو `Today / Study / Projects / Practice / Library`؛ Subjects
داخل Study، وDrawing Coach داخل Practice، وTasks سياقية، وSearch عام،
وSettings ثانوية، وUnified Workspace يفتح للمستند والملاحظة والرسم.

**الأثر:** لا يعاد استخدام تصميم P0 أو P3 القديم، ولا يتغير Core أو Schema.
تبقى قدرات محرك Ink واختباراته محفوظة، وتُبنى واجهته الجديدة لاحقاً داخل
Unified Workspace.
