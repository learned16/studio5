# Studio5 Standard Operating Procedure

**الإصدار:** 1.1

**الحالة:** مرجع تشغيلي دائم

**السلطة:** تنظّم هذه الوثيقة العمل ولا تتقدم على المرجع السلطوي أو قرار مستخدم أحدث.

## 1. الهدف

منع ضياع السياق، تضارب الوكلاء، التوسع الصامت، وفقد بيانات المستخدم. تُطبق هذه الحلقة على كل دفعة عمل:

`Requirement -> Task Brief -> Isolated Branch -> Implementation -> Verification -> Review -> User Approval`

## 2. الأدوار

| الطرف | المسؤولية |
|---|---|
| المستخدم | يحسم النطاق والقرارات الحساسة، يختبر على MatePad، ويوافق على الدمج |
| المخطط/المعماري | يكتب مهمة صغيرة ويحمي المواصفة والاعتماديات |
| Builder | ينفذ نطاق المهمة فقط ويشغل التحقق ويقدم أدلة |
| Reviewer مستقل | يراجع Diff والاختبارات والمواصفة ولا يعتمد على تقرير Builder وحده |
| GitHub | مصدر الفروع والتاريخ والمراجعة والرجوع |

## 3. دورة كل دفعة

1. أنشئ Work ID وRequirement IDs وحدودًا واضحة.
2. أنشئ ملف مهمة داخل `docs/tasks/` يحدد الملفات، خارج النطاق، القبول، والـRollback.
3. أنشئ فرعًا مستقلاً يبدأ بـ`codex/` ما لم يطلب المستخدم غير ذلك.
4. سجّل المهمة `IN PROGRESS` في `PROJECT_STATUS.md`.
5. نفّذ أقل تغيير يكمل المتطلب من دون Refactor جانبي.
6. شغّل Build وLint وType Check والاختبارات المناسبة.
7. راجع Diff كاملاً، واستخدم أدوات Guard إضافية فقط إذا كانت مثبتة ومتحققًا منها.
8. قدم التغيير لمراجعة مستقلة عند توفر المراجع.
9. أصلح الملاحظات المثبتة وأعد التحقق.
10. اختبر على الجهاز الحقيقي عندما يتعلق التغيير بالقلم أو PDF أو أداء الجهاز.
11. ارفع الفرع وحدّث الحالة بنتيجة حقيقية.
12. لا تدمج إلى `main` إلا بعد موافقة المستخدم.

## 4. قالب Task Brief

كل ملف مهمة يجب أن يحتوي:

- الهدف.
- Requirement IDs.
- الملفات المسموحة.
- خارج النطاق.
- العقود أو Migrations التي لا يجوز تعديلها.
- معايير قبول قابلة للاختبار.
- الاختبارات المطلوبة.
- دليل النجاح المتوقع.
- المخاطر المعروفة.
- خطة Rollback أو Recovery.

## 5. Definition of Done

- [ ] نطاق المهمة منجز بلا ميزات إضافية صامتة.
- [ ] Build/Lint/Type Check/Tests شُغّلت، أو وُثق بوضوح لماذا لا تنطبق.
- [ ] لا اختبار حُذف أو عُطّل لإخفاء فشل.
- [ ] تغييرات Schema لها إصدار وMigration واختبار Recovery.
- [ ] لا فقد بيانات ولا تعديل صامت لملف أو Ink أصل.
- [ ] الوثائق والحالة محدثة.
- [ ] قائمة الملفات المعدلة ونتائج التحقق والمخاطر موجودة.
- [ ] الفرع مرفوع، و`main` لم يُدمج آليًا.
- [ ] اختبار الجهاز الحقيقي موثق عندما ينطبق.

## 6. تقرير الدفعة

يصدر أحد الأحكام:

- `PASS`: النطاق مكتمل والأدلة المطلوبة ناجحة.
- `FAIL`: معيار قبول مثبت فشل.
- `NEEDS DECISION`: القرار يتطلب سلطة المستخدم أو توسعة نطاق.

ويحتوي التقرير على:

- ما تغيّر.
- الملفات المعدلة.
- أوامر ونتائج التحقق.
- ما لم يُختبر.
- المخاطر المتبقية.
- القرار المطلوب من المستخدم، إن وجد.

## 7. Change Control

أي حذف أو دمج أو تأجيل أو تغيير معنى ميزة، أو تغيير معماري/Contract، يجب أن يذكر:

- التغيير المقترح.
- السبب.
- الأثر على البيانات والنطاق والوقت.
- البدائل.
- توصية واضحة.
- قرار المستخدم.

يسجل القرار في `docs/DECISION_LOG.md`. لا يُعتبر سكوت المستخدم موافقة.

## 8. حماية البيانات

- Local-first للوظائف الأساسية.
- Autosave وJournal/Recovery قبل الميزات الثانوية.
- الأصول Immutable؛ المشتقات والـannotations منفصلة.
- لا Auto-merge لملفات رسم أو ملفات ثنائية معقدة.
- قبل Migration عالية الخطورة: Backup قابل للتحقق وخطة Recovery.
- فشل AI أو Sync أو Cloud لا يمنع الدراسة المحلية.

## 10. Academic Safe Mode

عند اقتراب امتحان أو تسليم مهم:

- لا Migration غير حرجة.
- لا ميزة تجريبية أو تحديث كبير.
- تُعطّل Feature Flags التجريبية.
- يزيد تكرار Backup عند توفره.
- تُقبل إصلاحات فقد البيانات والأعطال الحرجة فقط.

تفعيل هذا الوضع قرار مستخدم ويُسجل في `PROJECT_STATUS.md`.

## 11. العمل بين عدة وكلاء

- لا وكيلين على الفرع أو الملفات المحجوزة نفسها.
- المراجع يبدأ بتقرير فقط ولا يعدل فرع Builder في الجولة الأولى.
- تُنقل الملاحظات المثبتة إلى Builder للإصلاح.
- كل وكيل يقرأ آخر commit والحالة قبل العمل.
- لا تُستخدم ذاكرة المحادثة بدلاً من ملفات المستودع.

## 12. ما لا تفرضه هذه الوثيقة

- لا تفرض حزمة خارجية أو Skill غير مثبتة.
- لا تفرض Claude أو مزودًا بعينه.
- لا تعيد فتح قرار مستخدم محسوم.
- لا تجعل اكتمال Gate خاص بميزة واحدة حاجزًا لأعمال Core مستقلة عنها.
