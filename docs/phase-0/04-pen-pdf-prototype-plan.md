# Studio5 — خطة Prototype القلم وPDF

**الغرض:** إزالة أكبر المخاطر قبل اختيار التقنية وبدء كود المنتج.  
**الجهاز المرجعي:** يُثبت طرازه وإصدار نظامه قبل الاختبار.

## 1. ما الذي يجيب عنه الـPrototype؟

1. هل تصل أحداث القلم والضغط بشكل موثوق على MatePad؟
2. هل latency والاستقرار ملائمان للكتابة والرسم الدراسي؟
3. هل palm rejection يمكن الاعتماد عليه أو دعمه بسياسة إدخال آمنة؟
4. هل يمكن تثبيت الحبر فوق PDF عبر zoom/rotation وإعادة الفتح؟
5. هل التخزين المحلي المختار يتحمل جلسات طويلة وملفات كبيرة؟
6. هل Crash Recovery يعمل في السيناريوهات الواقعية؟
7. أي مسار تقني ينجح: Web/PWA + wrapper أم Flutter/Native بديل؟

## 2. ما ليس ضمن الـPrototype

- تصميم الواجهة النهائية.
- المواد والمهام والتقويم.
- تسجيل الدخول.
- السحابة والمزامنة.
- Drawing Coach الكامل.
- تحسينات شكلية.

## 3. مسارات الاختبار

### المسار A — Web-first

- صفحة Canvas بسيطة.
- Pointer Events مع pressure وpointerType.
- PDF renderer.
- تخزين محلي مناسب للـspikes.
- تشغيل في متصفح الجهاز ثم WebView/wrapper مرشح.

### المسار B — بديل مقارن

يُنفذ فقط إذا فشل A في معيار حاسم أو ظهرت قيود غير قابلة للعلاج. يختبر Flutter أو Native spike بأصغر نطاق مكافئ.

## 4. وظائف الـPrototype الدنيا

- فتح ثلاثة ملفات PDF ممثلة للأحجام الواقعية.
- رسم pen وeraser.
- تسجيل raw/coalesced events لأغراض القياس محليًا.
- pressure إن توفر.
- zoom/pan.
- تبديل الصفحة.
- حفظ strokes تدريجيًا.
- إغلاق وإعادة فتح.
- kill/relaunch recovery.
- تدوير الجهاز.
- تقرير قياس قابل للتصدير دون محتوى شخصي.

## 5. بروتوكول الاختبار على الجهاز

لكل build:

1. تسجيل طراز الجهاز، إصدار النظام، المتصفح/WebView، إصدار التطبيق.
2. تنفيذ خطوط بطيئة وسريعة ومنحنية وتهشير لمدة 5 دقائق.
3. اختبار الكف مع القلم ثم اللمس وحده.
4. رسم على أربع زوايا PDF وعند مستويين من zoom.
5. تدوير الجهاز مرتين.
6. التنقل بين 10 صفحات والعودة.
7. قتل التطبيق أثناء stroke وبعده مباشرة.
8. جلسة كثيفة 30 دقيقة، ثم جلسة تحمل 60 دقيقة للمرشح النهائي.
9. إعادة تشغيل الجهاز وفتح العمل.
10. تسجيل النتيجة: Pass/Degraded/Fail مع فيديو قصير عند العيوب البصرية.

## 6. القياسات

- median وp95 latency إن أمكن قياسها بصدق.
- معدل الأحداث الواردة أثناء stroke سريع.
- dropped frames / long tasks.
- peak memory للملفات الممثلة.
- حجم strokes قبل/بعد encoding.
- زمن autosave.
- زمن فتح/استعادة جلسة.
- مقدار البيانات المفقودة بعد kill.
- انزياح الإحداثيات بعد zoom/rotation.

## 7. بوابات القرار

### Go لمسار Web-first

- الرسم مقبول ذاتيًا على الجهاز المرجعي وفي اختبار متكرر.
- لا يوجد انزياح ملحوظ للحبر.
- recovery يحقق نافذة الفقد المعتمدة.
- ملف الاختبار الكبير لا يسبب crash متكررًا.
- يمكن منع/تصفية اللمس العرضي بدرجة مقبولة.
- التخزين المحلي يستعيد جلسة طويلة بصورة صحيحة.

### Conditional Go

- غياب pressure فقط، مع نجاح بقية الشروط، لا يمنع المنتج؛ يُوثق كقدرة منصة.
- ضعف ميزة غير أساسية مثل selection لا يمنع البدء إذا أمكن تأجيلها.

### No-Go

- latency أو jitter يجعل الكتابة غير عملية.
- palm input ينتج علامات لا يمكن ضبطها.
- WebView يفقد strokes بصورة متكررة.
- PDF الكبير يسبب crash غير قابل للمعالجة.
- التخزين أو recovery لا يمكن جعلهما موثوقين.

عند No-Go يُنفذ المسار B ويُعاد نفس الاختبار، ثم يُختار المسار الأعلى موثوقية لا الأسرع في إعداد demo.
