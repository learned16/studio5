# Studio5 Agent Rules

ابدأ بقراءة `AR_HERE_START.md` ثم هذا الملف و`PROJECT_STATUS.md` وملف المهمة الحالي.

## السلطة والنطاق

1. يتقدم أحدث قرار صريح ومؤرخ من المستخدم والمسجل في
   `docs/authority/STUDIO5_AUTHORITY_CURRENT_EN.md`.
2. تحكم `docs/authority/Studio5_One_Time_Full_Build_Spec_v5_AR.md` بقية النطاق.
3. تثبت الاختبارات والـPull Requests حالة التنفيذ، ولا تستبدل السلطة.
4. تُستخدم الوثائق القديمة للتاريخ فقط.

القرار الأحدث يعدل الجزء المتعارض فقط ولا يلغي المواصفة كاملة.

- Studio5 منصة دائمة لخمس سنوات، والتنفيذ الإنتاجي يعطي الأولوية لاحتياجات السنة
  الأكاديمية الحالية.
- السنوات اللاحقة ليست محذوفة من النطاق، لكن تفاصيلها وواجهاتها لا تُبنى قبل
  حاجتها الأكاديمية.
- يبقى Core والعقود ونموذج البيانات قابلين للتوسع عبر Profiles وFeature Flags
  ونقاط امتداد موثقة.
- Web/PWA هو مسار التنفيذ والإثبات الحالي، وليس المنصة النهائية الوحيدة.
- Phase 5 جزء من Gate D وليست نهاية Studio5.
- لا تثبت أسماء مواد السنة الحالية أو افتراضاتها داخل Core.

## تنظيم Codex المعتمد

- `A — Production`
- `B — Review & QA`
- `C — Prototype & Architecture`
- تستخدم مهام تسليم Studio5 مهارة `$studio5-delivery`، وتتوفر الأدوار الثلاثة
  كوكلاء مخصصين داخل `.codex/agents/`.
- الوكيل `B — Review & QA` مراجع مستقل ممنوع سلوكيًا من الكتابة ولا يصلح
  التغييرات بنفسه. يبقى `sandbox_mode = "read-only"` إعدادًا افتراضيًا، لكن لا
  يُدّعى أنه enforced عندما يعيد Codex تطبيق صلاحيات parent الحية القابلة
  للكتابة عند spawn؛ لذلك تحيط كل مراجعة B ببصمة repository حتمية قبل/بعد، وأي
  mutation يفشل المراجعة.
- تختار المهارة الوكلاء والتوازي حسب الحاجة؛ لا تشغّل A/B/C جميعاً افتراضياً.
- لا تُخزّن الحالة التشغيلية المؤقتة داخل هذا الملف؛ تُثبت من السلطة وGit وPRs
  والاختبارات عند بداية كل تشغيل.
- Blockers first.
- العمل المتوازي مسموح فقط عندما تكون المهمة `PARALLEL-SAFE`.
- تستخدم المهام المتوازية Worktrees وفروعاً مستقلة، وتكون الملفات المشتركة لمهمة
  واحدة في الوقت نفسه.
- Codex ينفذ؛ المستخدم والمشرف يحسمان.
- قبل تشغيل A أو B أو C يصنّف المشرف تعقيد المهمة وغموضها ومخاطرها وسياقها
  وحاجتها المعمارية وحساسية المراجعة وطبيعتها المتكررة، ثم يختار أقل طبقة
  model/reasoning متاحة تكفي ويسجل الدليل. لا يوجد pin عالمي؛ عدم توفر خيار
  مفضل يعني fallback آمنًا، ولا يقلل الاختبارات أو B أو guards أو بوابات البشر.
- نهاية كل مهمة: `Commit + Push + Draft PR + Tests + STOP`.
- لا Merge تلقائي.

## قواعد التغيير

- اقرأ `PROJECT_STATUS.md` لتعرف المنجز، العمل النشط، والخطوة التالية قبل بدء أي مهمة.
- لكل عمل جديد ملف مهمة داخل `docs/tasks/` وفرع مستقل. حدّث سجل العمل النشط قبل الكود وبعده.
- اربط المهمة بمتطلب في `docs/TRACEABILITY.md` عندما يكون المتطلب موجوداً، وأضفه عند إدخال قدرة جديدة.
- لا يعمل وكيلان على الفرع نفسه أو ملفات المهمة نفسها بالتوازي. إذا كانت المهمة محجوزة لوكيل آخر، توقف واختر مهمة مستقلة.
- اقرأ المهمة والوثائق ذات الصلة قبل التعديل.
- لا تعدل ملفات خارج نطاق المهمة.
- لا تحذف أو تدمج أو تؤجل أو تغير معنى ميزة معتمدة بصمت. أي اقتراح تغيير يذكر: التغيير، السبب، الأثر، البدائل، وقرار المستخدم المطلوب.
- لا تحول Studio5 إلى قارئ PDF أو تطبيق ملاحظات عادي.
- لا تدمج أي فرع في `main` دون موافقة المستخدم.
- اتبع دورة العمل والتسليم الموجودة في `docs/STUDIO5_SOP.md`.

## سياسة التجارب وقابلية الاستبدال

- اعتبر كل واجهة أو تدفق نبنيه قبل الاستعمال الجامعي الحقيقي **فرضية تجريبية**، حتى لو نجح Build والاختبارات والنشر. النجاح التقني لا يعني اعتماد الشكل كمنتج نهائي.
- افصل كل قدرة جديدة إلى حدود واضحة قدر الإمكان: `Core/Domain` ثم `Adapter/Bridge` ثم `Prototype UI` ثم إعداد النشر. لا تخلط منطق المجال داخل شاشة التجربة.
- لا تجعل Prototype يستورد ملفات Prototype آخر مباشرة. التكامل بين الميزات يمر عبر عقود Core أو واجهات موثقة قابلة للاختبار.
- اجعل لكل تجربة مجلداً وملف مهمة وفرعاً مستقلاً، مع قائمة ملفات محجوزة ومسار `Replace/Retire` واضح.
- يجب أن يكون ممكناً تعديل واجهة ضعيفة أو استبدالها أو إخفاؤها لاحقاً من دون كسر الوحدات الأخرى. لا يُسمح بحذف بيانات المستخدم عند تغيير واجهة التجربة.
- تغيير شكل UI حر ضمن مهمة مستقلة، لكن تغيير Contract أو Schema أو معنى البيانات يحتاج Change Control وMigration وRecovery.
- عند بدء الدوام، تُراجع التجربة وفق الاستخدام الحقيقي وتُصنف: `Experimental` أو `Accepted` أو `Revise` أو `Retired`. التقاعد يوقف الواجهة ولا يمحو البيانات تلقائياً.

## جودة التنفيذ

- شغل Build وLint وType Check والاختبارات المناسبة قبل التسليم. إن لم توجد بعد، اذكر ذلك صراحة ولا تدع نجاحاً غير موجوداً.
- لا تحذف اختباراً لإخفاء فشل.
- أدوات Guard الخارجية اختيارية حتى تُثبت وتُراجع؛ لا تُنزّل أو تفرض حزمة غير متحققة، ولا تعتبرها بديلاً عن الاختبارات.
- أي تغيير بيانات يحتاج schema version وmigration قابلة للاختبار وخطة rollback/recovery.
- احم بيانات المستخدم وملفات الرسم: لا حذف تلقائي، لا تعديل صامت للأصول، وAutosave/Recovery قبل الميزات الثانوية.
- قدم: الملفات المعدلة، نتائج التحقق، الأخطاء أو المخاطر المتبقية، ودليل نجاح قابل للفهم.
- عند توفر مراجع مستقل، سلّمه Diff وملف المهمة ولا تعدل أنت تقريره. راجع `CLAUDE.md`.
- حدّث `PROJECT_STATUS.md` بنتيجة حقيقية فقط: لا تضع `DONE` قبل نجاح التحقق ورفع الفرع.

## Git

- استخدم فرعاً خاصاً بكل مهمة.
- لا تعمل force push أو reset --hard أو إعادة كتابة تاريخ من دون موافقة صريحة.
- لا تدمج إلى `main` في أي مهمة آلية.
- لا تنفذ أي Merge تلقائي إلى أي فرع.

## تسليم الحزم المرجعية للمستخدم

يمكن تقسيم وثائق المستودع داخلياً عند الحاجة التقنية. أي حزمة مرجعية تُسلّم
للمستخدم مستقبلاً تُجمع في ملف عربي واحد باسم
`Studio5_Master_Current_AR.md`. لا يُنشأ هذا الملف إلا ضمن مهمة تطلبه صراحة.
