# سياسة Git المبسطة لمشروع Studio5

هذه الصفحة للمستخدم المبتدئ. القاعدة الأهم: لا تعمل مباشرة على `main`، ولا تضغط
Merge قبل نجاح الاختبارات وفهم ما سيتغير.

## الكلمات الأساسية

- **Repository:** مجلد المشروع مع تاريخ كل التغييرات.
- **Branch:** خط عمل منفصل يسمح بتجربة أو إصلاح من دون كسر النسخة التجميعية.
- **Commit:** لقطة محفوظة لمجموعة تغييرات لها رسالة واضحة.
- **Push:** رفع commits المحلية إلى GitHub.
- **Pull Request (PR):** صفحة تقارن branch مع branch آخر وتسمح بالمراجعة وCI.
- **Merge:** إدخال تغييرات PR في الفرع الهدف بعد الموافقة.

## الفرق بين main وdevelop

- `main`: النسخة الرسمية. لا ندمج إليها حالياً ولا نبدأ منها Phase 5.
- `develop`: النسخة التجميعية لأحدث المراحل المقبولة. كل feature جديدة تبدأ منه
  وتعود إليه عبر Pull Request.

## دورة العمل

```text
develop
→ feature/fix/chore branch
→ commits صغيرة
→ lint + typecheck + tests + build
→ push
→ Pull Request إلى develop
→ review وCI
→ موافقة المستخدم
→ merge
→ اختبار develop
→ حذف branch بعد التأكد فقط
```

## بداية مرحلة أو ميزة

1. تأكد أن `develop` محدث وأن CI أخضر.
2. أنشئ branch باسم واضح:
   - `feature/<name>` لميزة.
   - `fix/<name>` لإصلاح.
   - `chore/<name>` لتنظيم أو بنية.
   - `docs/<name>` للتوثيق فقط.
3. أنشئ ملف مهمة داخل `docs/tasks/`.
4. نفذ النطاق المكتوب فقط.
5. لا تخلط ميزتين غير مرتبطتين في commit واحد.

## قبل Push

1. راجع `git status`.
2. تأكد أن الملفات الشخصية أو الأسرار أو نتائج الجهاز غير المقصودة ليست staged.
3. شغل الأوامر الموجودة فعلياً في `package.json`.
4. راجع `git diff`.
5. استخدم رسالة Commit تصف النتيجة، مثل:

```text
docs: prepare phase 5 specification
fix: reject corrupted backup before migration
```

## عند فتح Pull Request

- الهدف الطبيعي هو `develop`.
- اكتب Work ID، الملفات، نتائج الاختبارات والمخاطر.
- لا تستخدم Auto-merge.
- لا تفتح إلى `main` إلا بقرار إصدار صريح لاحقاً.

## متى لا تضغط Merge؟

- CI فاشل أو لم يكتمل.
- يوجد اختبار MatePad مطلوب ولم يُنفذ.
- PR يحتوي ملفات لا تعرف سبب تغيرها.
- يوجد Migration بلا Backup/Recovery واختبار.
- يظهر تعارض لا تفهمه.
- PR يستهدف `main` بينما المطلوب `develop`.
- المراجع طلب تغييرات لم تُغلق.

## ماذا أفعل إذا فشل CI؟

1. افتح الفحص الأحمر.
2. اقرأ أول خطوة فشلت، لا آخر رسالة فقط.
3. لا تحذف الاختبار ولا تضف `continue-on-error`.
4. أصلح السبب في branch نفسه.
5. شغل الاختبار محلياً.
6. Commit وPush؛ سيعمل CI من جديد تلقائياً.
7. إذا كان الفشل من خدمة GitHub نفسها وليس الكود، وثقه وانتظر إعادة التشغيل.

## الرجوع عن Merge خاطئ

- لا تستخدم `reset --hard` ولا Force Push على الفروع المشتركة.
- أنشئ **Revert** للـMerge من GitHub أو:

```text
git revert -m 1 <merge-commit-sha>
```

- افتح PR بالـRevert إلى الفرع الذي حدث فيه الخطأ.
- إذا كان هناك تغير بيانات، نفذ خطة Recovery الخاصة بالمهمة قبل أي تشغيل جديد.

## متى يُحذف branch؟

بعد أن:

1. يندمج PR الصحيح.
2. ينجح CI على `develop`.
3. تنجح بوابة الجهاز إن كانت مطلوبة.
4. لا يحتوي branch ملفات أو commits فريدة غير منقولة.

الحذف ليس فورياً ولا آلياً في Studio5. فروع Sites القديمة تُوثق وتُؤرشف ولا تُحذف
قبل قرار مستقل.
